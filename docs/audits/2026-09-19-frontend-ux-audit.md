# Veyra: аудит фронтенда и UX

Дата завершения: 19 сентября 2026. Код: `b38c50b`.

Проверены текущий код, публичный deployment `https://agent-commerce-six.vercel.app` и 15 скриншотов пользователя. Предыдущие F1–F9 не переоткрывались: это отдельный аудит представления данных, навигации и пользовательских сценариев. На этапе аудита изменялся только этот отчёт. По последующему поручению пользователя выполнены исправления; их итог приведён ниже. Описания UI-01–UI-10 фиксируют состояние до исправлений, номера строк относятся к исходному коду.

## Вывод

Визуальный стиль уже узнаваем. Основная проблема — несогласованность трёх интерфейсов: персональная Nova, ручная покупка `/run`, developer console. Навигация, кошелёк и представление платежа меняются при переходе между ними. До косметического редизайна нужно устранить потерю локального доступа при сбоях и ошибки отображения денег.

## Подтверждённые проблемы

### UI-01 · P1 · Сетевой сбой удаляет сохранённый доступ к Nova

Источник: `app/nova/nova-client.tsx:303–320`.

Любая ошибка первоначальной загрузки brief вызывает удаление `veyra.nova.id` и `veyra.nova.key`. Это не ограничено ответом «агент не существует»: сюда попадают отсутствие сети, 5xx и ошибки разбора ответа.

**Воспроизведено в браузере:** установлены только искусственные id/key; для одного запроса brief подменён `window.fetch`, возвращающий отклонённый Promise `AUDIT_SIMULATED_OFFLINE`. После перехода через ссылку Memory: один перехваченный запрос, оба ключа отсутствуют, показаны ошибка и форма создания. Реальный агент и ключ пользователя не использовались.

Последствие: агент остаётся на сервере, но браузер теряет сохранённый доступ. Без отдельно сохранённого recovery key восстановление может оказаться невозможным.

**Исправление:** не удалять секрет при ошибке загрузки. Разделить временную недоступность, отказ авторизации и отсутствие агента; показывать Retry и восстановление. Забывание агента — отдельное явное действие. Сохранить возможность скопировать recovery key даже при недоступном API.

### UI-02 · P2 · На ширине 768–1023 px отсутствует основная навигация

Источники: `components/layout/topbar.tsx:39,85`, `components/layout/sidebar.tsx:199`, `components/layout/bottom-nav.tsx:28`.

Верхние ссылки включаются с `lg`, а hamburger, drawer и нижняя панель скрываются уже с `md`. На публичных страницах desktop sidebar отсутствует.

**Воспроизведено:** при ширине 820 px все три элемента имеют `display: none`. Это касается планшетов, уменьшенного окна и некоторых режимов масштаба desktop-браузера.

**Исправление:** согласовать breakpoint всей оболочки. Проверять не только отсутствие горизонтального скролла, но и доступность всех основных разделов.

### UI-03 · P2 · Desktop и mobile показывают разные продукты

Источники: `lib/navigation/sidebar.ts:55`, `components/layout/bottom-nav.tsx:8`, `components/layout/layout.tsx:15`.

| Поверхность | Пункты |
| --- | --- |
| Desktop header | Today / My Agent / Memory / Arc |
| Mobile drawer | Today / My Agent / Memory / Arc |
| Mobile bottom bar | Brief / Decisions / Advanced |

`Advanced` открывает `/run`, который исключён из общей оболочки. Исчезает нижняя навигация, меняются шапка и управление кошельком. Возврат через логотип существует, но переход выглядит как открытие другого приложения.

Это объясняет присланные скриншоты. Страницы `/executions` и `/run` существуют и на desktop, но входы в них находятся в console. Причина — разные массивы маршрутов, а не установленная отдельная мобильная версия.

**Исправление:** один источник навигации для всех размеров. Одинаковые названия и пункты; ручную покупку и developer console вынести во вторичный раздел. Console-ссылки на маршруты вне `/console` также сейчас теряют console-оболочку: это нужно решить явной принадлежностью маршрута или заметной ссылкой возврата.

### UI-04 · P2 · Connect wallet может ничего не объяснить пользователю

Источники: `components/layout/topbar.tsx:116`, `app/run/run-client.tsx:1125`, `components/wallet/use-arc-wallet.ts:244`, `components/wallet/connect-chip.tsx:50`.

Отсутствие кошелька в публичной шапке намеренное: `WalletWidget` рендерится только для console. Это продуктовый выбор, а не сломанный CSS.

Однако в `/run` верхний ConnectChip умеет предложить установку/открытие wallet app, а основная кнопка формы всё равно вызывает `wallet.connect()`. При отсутствии injected provider hook сохраняет ошибку; страница эту `wallet.error` не выводит.

**Воспроизведено:** в браузере без расширения верхняя ссылка предлагает Install a wallet, нажатие Connect wallet в форме не показывает ошибку или следующий шаг. На мобильном скриншоте те же две ветки выглядят как Open in wallet app сверху и Connect wallet внутри формы.

**Исправление:** общий сценарий подключения для шапки и формы; состояния обнаружения provider, открытия приложения, подключения, отказа и ошибки. Добавить в публичную шапку компактный необязательный Wallet: disconnected / адрес / текущая сеть / disconnect. Чтение brief оставить доступным без подключения.

Не переносить существующий WalletWidget без адаптации: его текст предназначен для hosted requester, а Nova и ручная покупка могут списывать средства из другого источника.

### UI-05 · P2 · Ссылки платежей не учитывают сеть

Источники: `app/executions/page.tsx:169–171`, `app/run/run-client.tsx:1532`, `app/execution/[publicId]/page.tsx:154`.

Decisions всегда строит URL на Arc Testnet. `/run` всегда использует Basescan. Квитанция выводит только `completeTx`, пропуская `paymentTx` обычного x402-платежа.

**Воспроизведено:** публичный API вернул для `vexec_f4590eac57694b9d` сеть `eip155:8453`; ссылка его транзакции в Decisions ведёт на `testnet.arcscan.app`. Квитанция `vexec_863e2ec6dfa24e16` не показывает имеющийся `paymentTx`.

**Исправление:** общий resolver по сети конкретной транзакции; отдельно payment transaction и Arc attestation. Использовать безопасный публичный DTO, в котором уже есть `x402.network`; не возвращать в UI секретные поля исходного execution ради совместимости типов. Если сеть неизвестна, не угадывать explorer.

### UI-06 · P2 · Квитанции округляют микроплатёж до нуля и не показывают уровень доказательства

Источники: `app/execution/[publicId]/page.tsx:67,81`, `app/executions/page.tsx:85,236`, `lib/execution/public-view.ts`.

**Воспроизведено:** API сообщает 0.001 USDC для `vexec_863e2ec6dfa24e16`, а Requested Amount и Actual Settled в квитанции показывают `$0.00`. Общая сумма 0.018 USDC в Decisions округлена до `$0.02`.

Кроме того, backend различает `presumed_spent`, `seller_reported`, `facilitator_accepted`, `onchain_final`, но ledger/receipt этот `settlementProof` не выводят. Это вывод из кода; все семь просмотренных исторических записей имели null, поэтому наличие новых записей каждого уровня в production не утверждается.

**Исправление:** единый формат USDC, сохраняющий значимые знаки до шести десятичных; ненулевое значение никогда не печатать как ноль. Разделить «разрешено», «учтено в бюджете», «подтверждено списание», «проверен результат». Для старого null показывать «уровень подтверждения не записан».

### UI-07 · P2 · Фильтры и жизненный цикл расходятся со статусами execution

Источник: `app/executions/page.tsx:29–77,90–96,223`.

`Settled` фильтрует только `COMPLETED`, `Refused` — только `FAILED`; Waiting и In flight тоже сравнивают единственное значение. Поэтому `SETTLED_SERVICE_FAILED` не находится через Settled, а `SETTLEMENT_FAILED` не находится через Refused. Терминальные состояния вне массива этапов также не получают корректно отмеченный достигнутый этап.

**Воспроизведено:** при семи записях (три `SETTLED_SERVICE_FAILED`, четыре `SETTLEMENT_FAILED`) оба фильтра Settled и Refused дают пустой результат.

**Исправление:** общая модель отображения состояния, отдельно результат платежа и результат услуги. Человекочитаемые подписи: «Оплачено · результат не прошёл проверку», «Платёж не прошёл», «Подтверждение ожидается». Не объединять экономическое списание и качество ответа в одно слово Refused.

### UI-08 · P2 · My wallet фильтрует получателя, а не плательщика

Источники: `app/executions/page.tsx:203`, `app/api/execution/v1/route.ts:22`, `lib/execution/db.ts:419`.

Кнопка My wallet передаёт подключённый адрес как `counterpartyWallet`; запрос сравнивает его с `counterparty_wallet` продавца. Для покупателя результат не соответствует ожидаемой истории его трат.

**Подтверждение:** прослежен код UI → API → БД; реальный кошелёк не подключался.

**Исправление:** определить роль фильтра явно: Paid by me / Received by me. Для первого использовать плательщика, для ERC-8183 — buyer из соответствующей модели. Не делать вывод о владельце из адреса контрагента.

### UI-09 · P2 · Ошибка API выдаётся за отсутствие истории

Источник: `app/executions/page.tsx:199–213,316–338`.

При первом неуспешном запросе остаётся пустой массив, loading выключается, показывается «No decisions recorded yet». После успешной загрузки сбой оставляет старые данные без признака устаревания.

**Воспроизведено:** только в тестовом browser context ответ `/api/execution/v1` подменён на HTTP 503. Интерфейс сообщил, что решений ещё нет; ошибка не показана. Сервер не изменялся.

**Исправление:** самостоятельные состояния loading / empty / error / stale; Retry и время последнего успешного обновления. Не выдавать недоступность за нулевые расходы.

### UI-10 · P2 · Скрытое мобильное меню остаётся доступным с клавиатуры

Источник: `components/layout/sidebar.tsx:195–217`.

Закрытый drawer скрывается через transform, pointer-events и aria-hidden; это не исключает дочерние кнопки из Tab-порядка. У открытого меню нет обработки Escape и управления фокусом.

**Воспроизведено:** на 390 px Tab после колокольчика переводит фокус на Close navigation внутри `aria-hidden=true`. Ранее Escape после открытия не закрыл меню.

**Исправление:** полноценный dialog/drawer: исключение закрытого содержимого из фокуса, перенос и удержание фокуса, Escape, возврат фокуса, видимая кнопка закрытия и блокировка фоновой прокрутки.

## Что ещё требует внимания

- **Тесты:** `npm run frontend:ux-test` падает на `README must remain under 220 lines` (README: 314 строк), до проверок UI. `frontend-responsive-smoke.mts:134` пытается найти Decisions в mobile drawer, где уже только Today / My Agent / Memory / Arc. Полный responsive suite не запускался; устаревшее ожидание подтверждено чтением. Тесты должны проверять пользовательские переходы и данные, а редакционные ограничения README — отдельно.
- **История ограничена последними 50 записями:** API использует default limit 50, UI суммирует только полученный массив, не показывает пагинацию или подпись «последние 50». На текущих семи строках это ещё не проявилось. До роста данных нужны total/период и cursor pagination.
- **System Operational в console — строка в коде**, не результат health check (`components/layout/sidebar.tsx:174`). Подключить реальную проверку с временем обновления или оставить только версию.
- **Между устройствами Nova восстанавливается recovery key.** Подключить тот же EVM-адрес недостаточно: локальная identity хранится отдельно. Deeplink в wallet app переносит URL, но не localStorage и несохранённые поля формы. Нужен объяснённый сценарий восстановления/продолжения. Никогда не передавать recovery secret в URL. Сам переход в установленное wallet app здесь не проверялся.
- **Поддерживаемость:** NovaClient — 2823 строки, RunClient — 1631. Выделить wallet/session state, загрузку данных и общую модель платежа, затем компоненты страниц. Это должно сопровождать исправления, а не превращаться в отдельную перепись приложения.

## Предлагаемая структура интерфейса

Сохранить основные четыре направления, одинаковые на desktop и mobile:

| Раздел | Содержание |
| --- | --- |
| Today | Короткий brief и предлагаемые действия |
| My Agent | Интересы, режим, бюджет, подключённый кошелёк, восстановление |
| Memory | Вкладки Learned / Purchases; покупки с поиском и понятными статусами |
| Identity & Trust | ERC-8004 identity, история контрагентов, Arc attestations |

`Identity & Trust` — предлагаемое понятное название нынешнего Arc; Arc Testnet остаётся видимой сетью. Страница не должна называться What it has earned так, будто речь о доходе.

В шапке: бренд, основные ссылки, компактный Wallet, уведомления, вторичное More. Developer Console и Manual purchase доступны через More на обоих размерах. На mobile нижняя панель повторяет те же четыре основных пункта; drawer не предлагает другую карту продукта.

### Что упростить по присланным экранам

1. **Сегодня:** одна основная кнопка на карточке, Useful рядом; Follow / Not interesting / Ignore category — в меню. Явно объяснять действие до подтверждения цены.
2. **My Agent:** сначала имя, режим, бюджет и интересы; длинные параметры подписи — под Details. Also watching показывать группами по источнику с датой и числом обновлений. Повторы Parallel/Foundry видны на скриншотах, но это не доказательство дублей в БД: нужно отличать разные наблюдения одного источника.
3. **Memory:** отделить выученные предпочтения от покупок. Карточка покупки: вопрос, продавец, точная сумма, сеть, результат; hashes и provenance открываются по Details.
4. **Arc:** identity, ownership/access, attestations. Общую статистику трат не дублировать целиком из Memory. Ограничение переноса NFT и доступа к Nova оставить доступным и ясным.
5. **Console:** 5–6 верхних разделов и вложенные инструменты вместо длинного плоского списка. Сократить названия, которые сейчас обрезаются. Не удалять полезные функции вместе с их пунктами меню.
6. **Внешний вид:** сохранить фиолетовую тему, но снизить интенсивность свечения и текстуры вокруг плотных таблиц. Короткие статусные строки и заметные действия важнее одинаково больших декоративных карточек. Узкую колонку brief сохранить; ledger/console могут использовать ширину экрана лучше.
7. **Сети:** перед подписью показывать точную сеть платежа и источник средств; Arc attestation — отдельная строка. Глобальный Arc Testnet badge не должен создавать впечатление, что любая покупка использует тестовые USDC.

Это предложения по продукту, не доказанные программные дефекты. Контраст, реальные safe-area iOS и размеры touch targets требуют отдельного инструментального прохода; по скриншотам не объявляю соответствие или несоответствие WCAG.

## Очерёдность

1. UI-01: сохранность доступа при сбое.
2. UI-02–04: единая навигация и рабочее подключение кошелька.
3. UI-05–09: достоверная история денег, сети, фильтры и ошибки.
4. UI-10 и обновление браузерных regression tests.
5. Упрощение текста, карточек и console без смены визуальной идентичности.

## Проверка и ограничения

- Browser: публичные страницы, desktop 1280 px, tablet 820 px, mobile viewport 390 px; отдельный тестовый контекст без кошелька пользователя.
- Для UI-01 и UI-09 ошибки имитировались локальной подменой fetch. Никакие реальные ключи не вводились, платежи/подписи/деплой не выполнялись.
- `nova-presentation:test`: PASS, 52 assertions/claims.
- `nova:test`: PASS.
- `frontend:ux-test`: FAIL на ограничении длины README.
- Скриншоты дают дополнительное свидетельство о состоянии заполненного агента. Его персональные авторизованные страницы не воспроизводились через recovery key пользователя.
- Это аудит, а не заявление, что весь frontend или реальные Safari/wallet-app сценарии прошли end-to-end проверку.

### Дополнительные улучшения

- Добавлена cursor pagination по `created_at` и `execution_id`; граница страницы с одинаковыми timestamp не теряет записи. Курсор сохраняет исходную точность timestamp БД. API проверяет limit и формат курсора.
